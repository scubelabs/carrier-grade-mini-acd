# Engineering and learning contract

Read existing repository instructions and inspect code, current state and open issues/PRs before editing. Explain the problem, why it matters, architectural fit, changed components, alternatives and risks before implementation. Use a feature branch, preserve existing work, execute appropriate validation, record decisions and prepare a reviewable PR. Never merge, deploy, delete repositories or alter visibility without explicit user approval. Never publish private inventory or code in public documents.

For meaningful changes deliver a beginner-accessible walkthrough: what/why, architecture, files, important functions/interfaces/APIs, data/control flow, configuration/dependencies, build/run/test, troubleshooting, security/performance/scaling/reliability and next learning. Explain important logic line by line against the implementation commit. Include a practical lab and short knowledge check.

Track implementation complete, walkthrough available, exercise attempted and understanding validated independently. A merge, scroll, generated quiz answer or AI-run test never grants mastery. Update the verified current-state and next action with SHA, date and actual results. Respect repository-specific instructions; apply this standard proportionately rather than generating boilerplate or unnecessary tests.

For each meaningful PR, include these ten reviewable teaching sections (or link a versioned walkthrough containing them): 1. Problem statement and architectural context; 2. Implementation summary; 3. Changed files and purpose; 4. Important functions/APIs/configuration; 5. Data and control flow; 6. Decisions and alternatives; 7. Build/testing instructions and actual evidence; 8. Troubleshooting; 9. Beginner-to-advanced code walkthrough; 10. Existing Medha lessons and practical exercises. Use .github/PULL_REQUEST_TEMPLATE.md. Do not fill an evidence field with an expected output presented as an observation.
